# T37：行动、收入与终局

更新：2026-09-13。纯规则引擎位于 [actions.rs](../game_core/src/actions.rs)，建立在 T34 冻结数据、T35 快照和 T36 共享几何之上，已能从初始化状态推进到自然终局。T38 已接通 [服务端事务与恢复](AUTHORITATIVE_GAMEPLAY.md)，浏览器棋盘操作由 T39 接入。

## 行动入口与原子性

```rust
use game_core::actions::GameAction;

let transition = snapshot.apply_action(authenticated_user_id, GameAction::Advance)?;
// transition.state：经过完整校验的新快照
// transition.events：按发生顺序排列的领域事件
// snapshot：保持原样
```

GameAction 是内部 Rust 类型，三个动作沿用已有协议意图，没有增加第二套网络命令：

| 动作 | 输入 | 完成的规则 |
|---|---|---|
| Advance | 无位置参数 | 到对手下一格、终点截断、实际步数奖励、轨道结算 |
| BuyAndPlace | PatchId、BoardPosition、Orientation | 候选/余额/几何校验、取布、中立移动、扣费、落子、收入更新、奖励和时间推进 |
| PlaceSpecialPatch | BoardPosition | 放置当前队首 1×1，检查奖励，自动处理满图版和终局 |

行动者由 authenticated_user_id 映射，目标固定是自己的图版；客户端不能自报另一个座位替对方行动。特殊拼布的身份由保存的队首决定，与已有 place_special_patch 只携带坐标的协议一致。

apply_action 先验证输入快照、身份、运行状态、行动者与阶段，再在副本中计算。只有最终状态通过 validate 才返回结果。余额不足、候选错误、越界/重叠、暂停、终局、错误阶段，以及数值溢出均返回错误，不修改原状态。所有纽扣加法使用 checked_add；即使购买已在副本中扣费、取布，而后续收入溢出，整份副本也不会提交。

这保证的是核心计算原子性。T38 已在 Actor 串行路径上校验会话、代次、expected_version 和 request_id，将新状态、事件、回执、终局结果放进同一数据库事务，提交后才广播。不能提前把 transition.state 覆盖到正式内存，也不能把客户端完整快照作为权威输入。

## 普通行动与收入

前进目标为 `min(对手时间 + 1, 53)`，奖励为截断后的 `新位置 - 旧位置`。前进奖励与图版收入分别记录。例如从 50 前进、对手在 53，实际只走 3 步，拿 3 个纽扣，再领取经过收入点 52 的图版收入。

购买按以下顺序计算：

1. 验证当前三个候选、姿态、落点和支付前余额。
2. 移除供给、中立标记移至空槽，扣费并保存占格与姿态。
3. 将该拼布收入加一次，检查首次连续 7×7。
4. 按时间成本推进，截断到 53，再结算轨道标记。
5. 处理特殊队列、下一行动者或终局。

例：开局购买 ID 12，费用 5、时间 4、收入 2。余额先从 5 变为 0，落子后收入为 2，移动到 4 正好触发收入，最终余额为 **2**。不会按这块拼布的 5 个格子重复累加收入；也不能用尚未收到的轨道收入支付当前购买。

两类行动共用 move_time。它按轨道位置升序处理 `(旧位置, 新位置]`，收入与特殊拼布领取交错记录。收入点一直保留，双方各自经过时领取自己的当前收入；离开标记不再次领取。购买的新拼布已经计入本次收入。终点没有新增收入标记，53 以外的时间和步数均不参与结算。

普通行动后，时间仍落后者继续行动；同格换成上一普通行动者的另一方。开局没有上一行动者时使用保存的先手。

## 特殊拼布、奖励与结束

- 首次经过未领取的特殊拼布时，立即在快照中写入领取者，并按轨道顺序加入队列。后经过的玩家跳过这块已领取拼布。
- 队列存在时只能由领取者放置队首。特殊布不收钱、不耗时、不加收入，不修改 last_normal_actor；不允许跳过或继续普通行动。
- 每次落下普通或特殊拼布都检查连续 7×7。只有全局 owner 为空时才写入领取者并产生 BonusAwarded；7 分与可花费纽扣分开。对方后来完成满区也不会覆盖归属。
- 图版已满时，已领取的特殊拼布自动转为 Discarded，原因固定 BoardFull，并逐块记录事件。这既覆盖普通购买填满后新领取的特殊布，也覆盖放下队首后刚好填满、剩余队列无法再放的情况。
- 双方都到 53 且队列清空后，自动保存 GameResult、切换 Finished 并产生一个 GameFinished 事件。总分为余额 + 所有者的 7 分，不扣空格分；等分 Draw，否则总分大者胜出。
- 终局后所有游戏行动返回 GameFinished 错误。重复恢复结算不会增加结果或奖励事件。

settle_automatic 是恢复/系统入口：对有效运行快照处理满图版队列和 AwaitingScoring。它不推进时间、不扣费、不替玩家选落点；非满图版的待放队列会继续等待。已结束快照原样返回、events 为空；暂停时拒绝结算，等待网络层完成恢复。每次正常 apply_action 已自动调用同样的处理逻辑。

## 事件与恢复边界

ActionEvent 包含 PatchPurchased、AdvanceReward、TimeMoved、IncomeReceived、SpecialClaimed、SpecialPlaced、SpecialDiscarded、BonusAwarded、GameFinished。事件带上相关玩家、金额、轨道位置、放置记录或结果，可用于账目和动画；GameFinished 始终在该行动的最后。

T38 将有序 ActionEvent 列表和该次完整结果状态放入 game_transition_v1，通过现有 GameEvent.payload_json 发送，数据库外层保存 seq/version；一次行动即一个事件批次。恢复直接安装已提交状态，不重新执行收入或扣款。引擎不接受任意事件正文来改状态。

快照 schema_version 仍为 1，T38 没有增加快照字段或数据库迁移。正式规则已允许权威开局。with_connection_pause 只改变连接生命周期；terminate 接受 Forfeit/Abandoned 并保留实际分数，供认输、断线弃权和废弃结果使用；自然计分仍经过 apply_action/settle_automatic。两个新核心测试覆盖暂停时的特殊队列及重复终止拒绝，网络和事务验收见权威对局说明。
