# Patchwork 完整对局开发方案

日期：2026-09-13。依据用户规则与补充确认制定，对应 [开发 TODO 阶段 7](DEVELOPMENT_TODO.md)。T34–T37 的规则数据、状态、共享几何和完整行动已实现；T38 已接通 [权威服务端、事务与恢复](AUTHORITATIVE_GAMEPLAY.md)。T39 已接入 [Bevy 联机棋盘与交互](FRONTEND_GAMEPLAY.md)，页面默认创建正式规则；T40 的完整边界与故障验收继续推进。

## 1. 已确认的规则

| 项目 | 本项目规则 |
|---|---|
| 玩家视角 | 左侧对手图版、右侧自己图版，均为 9 × 9；视角跟随登录身份，不固定绑定房主 |
| 初始资源 | 每人一个时间指示物、5 个纽扣；公共纽扣供给无限 |
| 拼布供给 | 每局将外围普通拼布随机排列一次；中立指示物初始放在 1 × 2 拼布之前 |
| 可选拼布 | 沿约定方向，中立指示物之后的三块剩余拼布；三个绿色脉动框标识候选 |
| 行动顺序 | 时间位置落后者行动，可以连续行动；同格时由刚完成普通行动的另一名玩家行动 |
| 开局先手 | 沿用房间已随机确定并持久化的 first_player_seat |
| 前进行动 | 前进到对手时间位置的下一格，超过终点则停在终点；获得实际移动步数等量的纽扣 |
| 购买并放置 | 从三个候选中选一块，允许旋转和翻折；支付纽扣并合法放置，中立指示物移到被取走拼布的位置，再按其时间成本推进 |
| 特殊拼布 | 首次经过对应位置者取得该位置的 1 × 1 特殊拼布；此后对手不能再领取 |
| 纽扣收入 | 每次经过纽扣标记，获得自己已经放置的普通拼布所示收入之和 |
| 7 × 7 奖励 | 全局首位完整覆盖任意一个连续 7 × 7 区域的玩家获得 7 分，只颁发一次 |
| 结束 | 双方时间位置都达到终点后结束；超过终点的距离不再推进，也不额外触发收入 |
| 计分 | 剩余纽扣数 + 获得的 7 × 7 奖励；不扣空格分，分数较大者获胜 |

这是本项目的明确规则：**同格换另一名玩家、不扣空格分**。不能在实现时替换成其他版本的同格顺序或计分方法。独立规则版本 patchwork_custom_v1 已完成数据冻结、注册和服务端开局接入。

### 已冻结的边界约定

- 遍历方向统一为界面顺时针。初始三个候选包含 1 × 2 拼布；用“中立标记 → 1 × 2 → 第二候选 → 第三候选”固定前后语义。
- 路过标记的结算区间定义为 old_position < marker_position <= new_position，包含本次落脚格，不重复结算出发格。
- 等分按平局处理，不额外引入“谁先到终点”规则；用户已确认。
- 特殊拼布须先完成放置再开始下一次普通行动；图版已无空格时，自动弃置该特殊拼布并记录原因，避免卡住对局。用户已确认此边界；不退还到公共轨道或发给对手。
- T34 按现有项目数据冻结起点 0、终点 53；纽扣点为 4、10、16、22、28、34、40、46、52，特殊拼布点为 19、25、31、43、49。33 块拼布的形状、费用、时间、收入已迁移并校验，明细见 RULES_DATA.md；这是本项目版本的明确选择。

## 2. 开局随机排列与中立指示物

### 数据和持久化

由后端在首次有效开局时生成一次排列，核心规则通过参数接收排列与先手，不依赖随机数或系统时间。Fisher–Yates 等洗牌实现放在服务端，测试注入固定排列。

保存完整 initial_supply_order、规则版本、先手和初始中立位置；不能只保存随机种子，也不能让两个客户端各自洗牌。开局幂等重试、刷新、重连与进程恢复必须使用原排列。

每块拼布分配稳定 PatchId。1 × 2 起始拼布通过定义 ID/几何校验定位，不依赖当前 Vec 下标；核对表中恰好存在一个符合条件的起始拼布。

### 位置表达

保留初始 33 个槽位，取走拼布后槽位为空，剩余拼布不整体重排。这样外围实体与动画位置稳定，重连也能恢复同一圈。

中立位置用两种含义区分：

- BeforeSlot(slot)：开局在 1 × 2 的槽位之前，从该槽位开始找候选。
- OnVacatedSlot(slot)：购买后位于刚取走拼布的空槽，从下一槽开始找候选。

沿环形槽位循环扫描，跳过空槽，最多取三块尚在供给中的拼布。不足三块时只标识实际剩余数量，供给为空时普通行动只剩“前进”。

例如候选依次为 A、B、C，后面是 D、E：选择 B 后，中立标记到 B 的空槽，新候选为 C、D、E；A 仍留在供给中。

## 3. 核心状态与行动顺序

继续扩展已有 game_core，Bevy Entity、网络连接和数据库句柄不进入核心状态。

| 数据 | 用途 |
|---|---|
| PatchDefinition | 稳定 ID、格子坐标、button_cost、time_cost、income；替换含义不够明确的 bt 元组 |
| PlayerState[2] | 玩家/座位、独立图版、已放拼布、纽扣余额、收入总额、时间位置 |
| SupplyState | 初始槽位排列、剩余拼布、当前中立位置 |
| TimeTrackDefinition | 起点、终点、有序纽扣点和特殊拼布点 |
| SpecialPatchState | 每个轨道特殊拼布的领取者与是否已处理，不只保存可 pop 的位置数组 |
| ActionState | 当前普通行动者、上一名普通行动者、待放特殊拼布队列 |
| BonusState | 首个 7 × 7 奖励获得者，None 或唯一玩家 |
| GameResult | 双方余额、奖励分、总分、获胜者或平局 |

图版占格与已放拼布必须按玩家分开。收入按每块已放拼布统计一次，不能按它占据的格子数重复累计。

普通行动完成后：

1. 如有待放特殊拼布，继续由领取者处理；对手暂不能行动。
2. 特殊拼布全部处理后，检查是否双方都到终点。
3. 未结束时，时间较小者行动；位置相同则选择上一名普通行动者的另一名玩家。
4. 初始同格使用房间的 first_player_seat，不把旧 last_move_tick 的初值当作正式先手。

放置特殊拼布不推进时间，也不改写“上一名普通行动者”，避免它影响同格换人的规则。连接暂停/恢复属于对局生命周期状态，与“等待普通行动/等待特殊拼布”分别保存。

## 4. 两类普通行动与轨道结算

### 前进

new_position = min(opponent_position + 1, track_end)。

advance_reward = new_position - old_position，使用截断后的实际步数；加到自己的纽扣余额。然后调用统一的轨道结算。

示例：A 在 8，B 在 10，A 前进到 11，获得 3 个纽扣，再结算区间 (8, 11] 中的轨道标记；待放特殊拼布处理完后由落后的 B 行动。购买后仍落后的玩家则可继续普通行动，不按固定轮流方式换人。

### 购买并放置

客户端已有协议 GameRequest.buy_and_place，携带 patch_id、position、quarter_turns、flipped；只提交动作意图。

服务端先校验身份/连接代次、版本、行动者、阶段、三个候选、余额、变换与落点。合法后一次性计算并提交：

1. 从公共供给移除选中的拼布，中立指示物移到对应空槽。
2. 扣除纽扣费用，写入自己的图版及已放拼布，更新收入总额。
3. 检查首次 7 × 7 奖励。
4. 按拼布时间成本推进，终点截断后结算轨道标记。
5. 进入特殊拼布放置阶段，或确定下一名行动者/终局。

预览、旋转、翻折、取消都不发送购买命令。扣费、中立移动和落子作为一个原子动作提交；不能先扣钱，再等用户摆放或取消。

### 共用的轨道处理

前进和购买都调用同一个规则函数，按位置升序处理 (old_position, new_position] 内的标记：

- 纽扣标记不从公共轨道移除。每名玩家各自在经过时获得当时的图版收入，因此同一个标记可以分别给双方结算。
- 购买行动先放入新拼布再移动，所以本次越过纽扣点时，新拼布的收入已经生效。
- 未领取的特殊拼布立刻登记领取者并加入其待放队列；已领取的跳过。一次跨过多块时按轨道顺序入队。
- 特殊拼布为 1 × 1，不收纽扣、不花时间、不提供收入；每放一块都检查 7 × 7 奖励。
- 先处理完待放特殊拼布，再确定下一普通行动者与终局。最后一次移动触发的收入与奖励必须计入最终分数。

终点示例（53）：从 50 因时间成本 7 前进，最终只到 53，纽扣标记 52 结算一次。前进目标原本是 54 也只能到 53，移动奖励按实际距离计算；不能制造第 54 格或额外终点收入。

## 5. 旋转、翻折与放置交互

采用“点击选块 → 图版预览 → 调整 → 左键点击合法落点放置”，同时保留 Enter 和确认按钮，第一版不依赖拖拽。

| 操作 | 鼠标/触屏入口 | 键盘快捷键 |
|---|---|---|
| 选择拼布 | 点击三个候选之一，显示费用/时间/收入 | 后续可补候选焦点切换 |
| 定位 | 鼠标悬停显示半透明预览；点击合法格子直接放置，触屏走同一 Pointer 路径 | 可用方向键微调预览落点 |
| 顺时针旋转 | “右转 90°”按钮 | R |
| 逆时针旋转 | “左转 90°”按钮 | Q 或 Shift+R |
| 翻折 | “翻面”按钮 | F |
| 提交 | 左键点击自己图版的合法落点，或点击“确认放置” | Enter |
| 取消普通拼布预览 | 游戏区域右键或“取消”按钮，返回选块 | Esc |

选择拼布后保留费用、时间和收入说明，并预览“支付后余额/移动后的时间位置”。无效落点用红色轮廓和短原因提示，合法落点用绿色预览。确认前可以换位置或取消。

变换使用 quarter_turns = 0..3 与 flipped，统一规定“基础形状翻折 → 旋转 → 归一化坐标”；双方和服务端使用同一个核心实现。预览以所选落点为变换后包围盒左上角，旋转时保持这个落点，避免实体坐标和校验坐标不一致。

键盘快捷键仅在游戏放置状态且焦点不在房间输入框时生效。触屏和没有键盘的用户可以完成所有必要操作。非本人回合可查看拼布信息，不能开始正式放置。

特殊拼布直接进入 1 × 1 放置预览，同样支持左键点击合法落点、Enter 或确认按钮放置；旋转/翻面无意义，不启用。取消当前落点不等于放弃已领取的特殊拼布，不允许跳到下一次普通行动。

## 6. 前端组件与时间横条

### Bevy 实体组件

| 组件/资源 | 职责 |
|---|---|
| PatchView { patch_id, slot } | 外围拼布实体身份和稳定槽位 |
| NeutralMarker | 中立指示物的显示与槽位移动 |
| CandidatePatch / CandidateFrame | 由权威快照推导的候选集合及三个绿色框 |
| QuiltBoard { owner } / QuiltCell { owner, x, y } | 区分双方图版，只给自己的图版开启放置输入 |
| PlacedPatchView { owner, patch_id } | 已放拼布显示，不与外围供给实体混用 |
| PlacementPreview | 临时落点、旋转、翻折、合法性与选块信息，不写入正式快照 |
| TimeToken { owner } | 双方时间指示物身份；实际显示可由底部 Yew 组件承接 |

候选框保留常驻实体，仅在候选集合变化时更新/隐藏，使用时间驱动透明度缓慢脉动（建议周期约 1.2 秒），不用反复销毁创建实体。标识至多三个规则候选，剩余不足三块时只显示实际数量，耗尽时隐藏全部候选框；买不起或无合法落点的候选仍允许选中预览，并显示不能购买的原因，仅禁用确认购买，不能改变中立指示物决定的候选集合。开启减少动态效果偏好时改为常亮框。

### Yew 控件

- GameHud：双方纽扣、收入、时间、奖励与“轮到谁”，更新数值而不重建游戏画布。
- PlacementToolbar：旋转、翻面、取消、确认及费用预览；固定位置和尺寸，避免按钮文字改变导致跳动。
- PatchIncomeLabel：双方已放有收入拼布各显示一个 +N，定位在实际占格上；标记不拦截棋盘拾取。HUD 显示每次收入总和，经过纽扣点将该总和加到余额，领取收入不再次累加收入能力。
- TimeTrack：位于游戏区域最下方，显示起点/终点、刻度、纽扣点、特殊拼布剩余状态和双方时间指示物。
- GameResultPanel：余额、7 × 7 奖励、最终分数和胜负/平局。

时间横条使用两条指示物显示通道，同一格也能看清双方，不用视觉堆叠来暗示同格行动规则。特殊拼布被领取后明确显示已领取/领取者；纽扣标记一直保留。窄窗口减少数字标签密度，悬停或点击标记查看说明，整条轨道不横向滚动。

横条与操作栏占据明确的固定区域，棋盘画布使用剩余空间并保持完整缩放。沿用当前不闪动的请求反馈方式，在 1920 × 889、1366 × 768、960 × 720 下验收整屏布局。

## 7. 协议、数据库与恢复

现有 protocol.proto 已预留 Advance、BuyAndPlace、PlaceSpecialPatch、Resign，不另造重复协议。T38 接通已有动作入口，补充必要快照/事件语义，保留字段编号与兼容边界。

在现有 Room/Game/Persistence 流程上提交核心规则结果。游戏状态、事件、命令回执以及终局结果在数据库事务中保持一致；重复 request_id 返回原结果，不再次扣钱、取拼布、发奖励或增加事件。

真实初始状态替换新规则版本下的 friend_room_empty_v1；历史空对局不能被直接反序列化成完整对局。明确规则版本不兼容的处理，关闭任意规则字符串即可开局的路径。

恢复时必须还原外围排列、中立位置、双方图版/余额/收入/时间、奖励归属、特殊拼布领取与待放队列、当前行动者。前端目前仅认识 connection_state_v1 的补事件逻辑，需要同时升级；无法应用事件时请求完整快照，不猜测状态。

放置中的本地预览与已提交状态分开：提交结果未知时重试原请求；尚未提交的预览在恢复后按新版本重新校验。不能因为重连重置已经消耗的特殊拼布、随机排列或 7 分奖励。

## 8. 验收重点与开发顺序

1. **T34 规则和定义表**：先冻结本轮明确规则、旧数据校验以及未指定的边界。
2. **T35/T36 纯核心状态与几何**：开局排列、三个候选、双方图版、八种变换、同格换人。
3. **T37 完整规则闭环**：两种行动、共用轨道结算、待放特殊拼布、7 × 7 奖励和终局计分。
4. **T38 权威服务端接入**：现有动作协议、事务/回执、版本、恢复与真实开局状态。
5. **T39 前端交互**：中立指示物、绿色框、放置预览/旋转翻折、底部时间横条和结算界面。
6. **T40 双浏览器完整验收**：双方完成真实对局，并覆盖重连、重复请求、进程重启和终局幂等。

必须覆盖：唯一 1 × 2 定位、随机排列无遗漏/重复、环末尾跨界和空槽跳过、剩余 0/1/2 块、余额不足、错误玩家图版、八种变换与越界/重叠、连续行动与同格换人、一次跨过多个纽扣/特殊拼布、特殊拼布被双方先后经过、7 × 7 连续区域与全局唯一奖励、终点截断、待放特殊拼布期间到达终点、空格不扣分、同分结果、每个副作用的请求重放。

首次上线主线继续使用好友房，FIFO 匹配 T30–T33 暂缓。完成计划与文档不代表以上开发任务已完成。
